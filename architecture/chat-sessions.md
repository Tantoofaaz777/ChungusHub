# Chat, message tree & chats: architecture & maintenance

**Author's notes.** The document button between Chat actions and Steering opens `AuthorsNotesDialog`, a centered editor for this chat's `featureState.authorsNote.text`. Nonblank text activates the notes; clearing the box deactivates them, and a legacy `enabled` flag is ignored. There is no switch. Text saves automatically after 400ms of inactivity through `chatStore.updateChatFeatureState`. Closing waits for the latest write before dismissing, and navigation or browser backgrounding flushes pending text to the captured chat id. There are no Save/Cancel actions. A late close for the old chat cannot close a newer editor. This state is shared across the chat's branches and copied with the chat's opaque feature-state column. It only enters prompts through `{{authorsNote}}` (architecture/macros.md), independently of Steering.

The conversation model is a **tree, not a list**: `messages` rows link by `parent_id` + `sibling_index`, a chat's `active_leaf_id` picks the branch being viewed (root→leaf walk = the visible transcript), and `canon_leaf_id` preserves a legacy canonical timeline marker. Multiple roots are legal (seeded greetings are root-level siblings), so the structure is really a forest. Swipes, regenerates, edits-as-branch, and forks are all "new sibling + move the leaf".

**Two stores split the work.** [`chat.svelte.ts`](../src/lib/stores/chat.svelte.ts) (`chatStore`) owns chats: the chat list, `currentChatState` (chat + active path + `allMessages`, both flat, + streaming state), chat creation (`createChat` **requires** a `characterId`: no UI path creates a characterless chat; rows orphaned by a character deletion are the only characterless ones. Every new-chat entry point either has a character in hand or routes through the New chat flow in architecture/ui-shell-settings.md. Auto-title `<character> - YYYY-MM-DD` off the shared `utils/date.ts` `formatDate` rather than a second date recipe: year-first is load-bearing twice over, since a title is a stored string and the chats panel's Title sort compares it as text, so this is what makes that sort group by character and run chronologically inside each one (architecture/ui-shell-settings.md, "one numeric date shape"), pin to the version new chats with that character start on (`characterLibraryStore.chatVersionSeed`: the character's own default while that version exists, else the first one ever made, and deliberately NOT the active version, which says only which variant the library is editing; from then on the chat's own pin decides every request it makes, see architecture/library.md), seed First Message + alternate greetings as swipeable root siblings, stored **raw**, with `{{char}}`/`{{user}}` left literal so they resolve live at display and generation and a persona change reflows the greeting), deletion (immediate and final: the chats panel's confirm dialog asks first with the chat's real message count, per the destructive-act ladder in architecture/ui-shell-settings.md; the store deletes server-first so a failed delete changes nothing on screen, and refuses only the case no dialog can cover: a reply still streaming into that chat's rows), **bulk deletion** (`deleteChats`, behind the chats panel's picking mode: a cleanup of twenty old chats is twenty menus and twenty confirms otherwise, and no delete-confirmation setting fixes the repetition around the gate. Deliberately NOT a loop over `deleteChat`: that re-routes the open chat once per row, so a batch containing the chat you are in can land you inside another chat that is itself about to go, and it would refuse the whole selection over one streaming reply. Here the streaming refusal is per row and says which one was kept, the server pass stops at the first failure with the list still telling the truth about what is left, and the routing runs once at the end. The panel's confirm states both figures, chats and messages, because the second is the one nobody counts before agreeing to lose it, and its hold scales on the message total), post-delete routing rules (`routeAfterDelete`, shared by both paths: stay within the same character's story; a living character never drops to zero chats), `goHome` (the composer's home action: a real chat close back to the boot zero state, with active id and chat state nulled, memory cleared, welcome raised; callers use `messageStore.warnIfNavigationBusy()` to protect unsent prompt preparation/review; a dispatched generation keeps its own stream and chat when Home clears the view), and `syncReload` (remote-change refresh that never disturbs a local stream: a hint arriving mid-stream sets `missedSyncWhileStreaming` and replays when `endStream()` lands, because the server never repeats a hint and dropping it left the device stale until the next remote change; that replay is unawaited, so it is routinely in flight beside a mutation's own refresh, and coupling 4's ordering rule is what stops it publishing over one). **The stream is owned, not ambient.** `stream` (`{ chatId, content, thinking, continuingMessageId }`, opened by `startStream(chatId)`, closed by `endStream()`) is a field of the STORE and deliberately not of `ChatState`: a generation belongs to the chat that asked for it, never to whatever the reader happens to be looking at. Three rules fall out and all three are load-bearing. Tokens land on the stream record, which already names its owner, and every transcript surface paints from `visibleStream` (the stream only while its chat is the one on screen), so a reply still arriving in a chat the reader walked out of cannot bleed into the one they walked into. The composer asks the opposite question: `messageStore.isStreaming` is `stream !== null` app-wide, not the viewed chat, so leaving a chat mid-reply never reads as idle; read off the view it unlocks the composer of wherever the user landed and lets a second generation start beside the first, over the one `abortController`, which then reaches only the newer of the two. That app-wide flag is the composer's WHOLE busy state: `ChatContainer` hands `InputArea` a single `isStreaming` prop and no separate `disabled`, because "the app is generating" and "the composer is shut" are one fact, and it is what turns Send into a Stop that reaches the running reply. **That busy state has a second source, and it is the one a phone meets**: a reply being written for this chat that this page never started (`chatStore.liveElsewhere`, asked of the server on every load of the open chat, which covers all three doors: opening it, a `messages` sync, and the reconnect resync; `llm-status` in architecture/server-core.md). A generation outlives its socket but not the page's memory of it, so a discarded tab comes back to a chat that IS busy with nothing on screen saying so: it reads as idle, the send is refused by the server's single-flight rule, and the Stop that would clear it belonged to a page that no longer exists. The composer goes busy on it, prints how long the reply has been running (the figure that tells a merely slow model from a stuck endpoint, which is the reader's judgement to make and not the app's), and `cancelGeneration` sends that one by request id rather than through the abort controller it does not have. **Drafting stays open in that state alone**: there are no tokens here to watch, the reader is deciding whether to wait it out, and it is the rows that would START a turn that have to stay dead. It never doubles a reply this page is writing, which paints its own stream and carries its own Stop (`visibleLiveElsewhere` excludes it), and it never reports an engine call, which writes no turn and blocks nothing. And the generation paths close by refreshing the chat they were FOR (`chatStore.refreshChat(chatId)`; `refreshCurrentChat` is now that same call with the active id): a reply landing while the reader is elsewhere still has to carry its own chat up the list with its new time, and refreshing whatever is open instead re-reads a transcript nothing touched while the chat that changed keeps its old position. `refreshChat` reloads the transcript only when that chat is the one on screen, so the list row moves either way. The instant tree mutations keep `refreshCurrentChat`: they cannot span a navigation. Home may close the visible chat while a dispatched generation continues; its header and composer actions share `warnIfNavigationBusy`, which still refuses prompt preparation/review and unrelated mutations. The send, swipe and opening-scene paths mark dispatch only once their prompt/placement is captured, and clear it with the stream in `finally`. Both direct New chat doors still use the mutation guard. Editing, deletion and a second generation remain protected by the normal busy checks. chatStore also owns the per-chat **feature state** (`chats.feature_state`: the last-10 spent-one-shot steering history, this chat's own **background**, which it may wear instead of the app's (architecture/ui-shell-settings.md), and the claims this story makes for itself, the **connection** it sends on, the **persona** it plays as and the **preset** its prompt is built from, each a plain id or null for "follow the app", plus the **lorebooks** it attached, a list of ids that ADDS to what its cards bring rather than standing in for anything, so empty is a story that adds none and never one with no lore (architecture/ui-shell-settings.md, "A chat claims what it can name"); types + the pure `normalizeChatFeatureState` live in `types/chat.ts`, shared by this store and the db-sourced generation path so both normalize identically, and the background half is coerced through the same normalizer the background store uses for its app-wide blob, so a chat's copy can never be trusted further than the app's): `featureState(chatId)` is the normalized reactive read, and `updateChatFeatureState`/`pushSteeringHistory`/`setImpersonatePerspective` are read-merge-write mutations serialized per chat through `featureStateQueues` (the same idiom as the message queue). `pushSteeringHistory` records the texts of spent one-shot steering notes, newest first (`pushSteeringHistoryEntry`: exact duplicates move up instead of duplicating, cap 10), and no-ops on an empty list so a turn with no one-shot never touches the row. **Steering itself does not live here**: notes are their own rows with their own scope and their own store (architecture/engines.md), and this blob keeps only the reuse list. A `steering` key left in an older blob is not parsed. [`messages.svelte.ts`](../src/lib/stores/messages.svelte.ts) (`messageStore`) owns turns: send (build the user turn → `prepare` → write it → generate), `generateResponse` (`llmService.complete` **carrying the turn's placement** → the server writes the turn and spends the one-shot notes → refresh, record the reuse list). **The two generations that create a turn do not write it: the server does** (`commit` on the request, `commitGeneratedTurn` server-side, architecture/server-core.md). A generation outlives the page that asked for it, so a phone whose browser is discarded mid-reply would otherwise have nowhere to put the answer it paid for, and the reply the reader is owed would exist only in a tab that is gone. What is left here is what only this side knows: the token calibration sample, the chat's steering reuse list (per-chat state the server deliberately does not author). The store learns the turn's id from `result.committedMessageId`, which is **null exactly where no row was written**: a stop that kept nothing, or a chat deleted while the model was writing. Every caller's "nothing was produced" branch reads that one field instead of re-deriving the stop contract. **Stop keeps what streamed**: an aborted generation comes back as an ordinary result flagged `cancelled` carrying every token that arrived before the stop (architecture/client-data-layer.md), and those are persisted as the turn like any other reply: the user watched the text arrive and stopped because they had enough of it. Only a stop with nothing to keep (no token yet, or a dead socket the server never answered through) creates no row and returns null, which is the one case the callers' abort branches still handle, edit (`save_only` / `create_branch`: the intent is picked by the button that opened the editor, Edit vs Branch, and never asked at save time; manual summaries are resolved against the saved source signatures after edits, while `create_branch` leaves the original chat and its summaries unchanged), delete (`this_only` splices: children re-parent via `deleteMessageOnly`, and the view re-homes ONLY when the deleted turn was the active leaf itself: nearest sibling branch preferring a same-role variant, else a re-parented child, else the parent; a mid-path splice keeps the leaf, which survives the delete, so the user never gets yanked to another branch, and re-parented children that land off the viewed path get an explanatory toast since they'd otherwise read as deleted; subtree delete is **final**: the confirm dialog is the only gate, rows and their attachment files go together, no undo), regenerate (`replace` snapshots the alternatives and removes their subtrees only in the successful reply transaction; cancelled, empty or failed replacements preserve them. `branch` generates a new alternative and keeps existing versions. Both stream into the selected bubble while its saved row remains intact; see architecture/swipes.md) and `regenerateLastResponse` (the composer's shortcut into it), sibling navigation, `generateOpeningScene` (the direction rides as a virtual user message that is never persisted, and the scene lands as a new **root sibling** appended after whatever roots the chat already holds: a beginning beside the card's greetings, never a replacement for one. Its index comes from `db.getNextSiblingIndex(chatId, null)`, one call against fresh rows rather than a count over a transcript pulled onto the wire for that number alone. `rootMessageId` is claimed only when nothing held it, since that pointer names the chat's FIRST root and an opening written beside existing greetings must not renumber which of them that is; the leaf moves to the new scene, because it is what the reader asked for, unless they have moved on since: the commit takes the leaf only while it still reads what the request left it on, so a scene landing after the reader walked elsewhere arrives as a root sibling they can swipe to rather than yanking them onto it. See architecture/engines.md for the doors and the engine's own contract), `continueMessage` (fired from the newest reply's own Continue button: extends the newest assistant turn **in place**; rebuilds the turn's regenerate prompt from fresh rows and rides the turn as the assembly's continuation tail, whose instruction is the active preset's own `continuePrompt`, resolved inside assembly; it is NOT an engine and takes the primary connection like any send, see architecture/prompt-pipeline.md; streams into the existing bubble via `ChatState.continuingMessageId`; on success writes the joined text + accumulated stats through `db.applyMessageContinuation`, which deliberately never stamps `edited_at`; manual summaries resolve against the updated source text; join rules (glue seam + restating-tail hold for the live preview, restatement trim for the persisted result, both matching in a NORMALIZED space since a model re-typing text swaps quote/dash/ellipsis styles and whitespace runs, and both anchored on `BuiltPrompt.continuationSent`, the turn's text as the model actually received it, because a macro-laden greeting is restated in its expanded form and comparing against the stored bytes appends the copy twice) live in [`utils/continuation.ts`](../src/lib/utils/continuation.ts), tested in `continuation.test.ts`; a stop keeps the tail that streamed and joins it exactly like a completed continuation, while a stop with nothing to keep, or a nothing-new result, discards it and touches no row), and `insertDummyMessage`. `warnIfBusy()` is the concurrency gate: every tree mutation checks it so nothing forks the lineage a streaming turn is about to attach to.

**Nothing a held generation would write happens before the reader releases it.** `prepare(gate, context)` is the one door into a story prompt: flush steering → `buildPromptMessages` → `promptHoldStore.review` (architecture/prompt-pipeline.md), returning null when the review was cancelled. Every caller reads that null the same way, and it is what decides where each path does its writing. A send **builds** its user turn (`buildMessageRow`) and prices the prompt against it as the last turn of the path, then inserts that same object only after the release, so a cancel leaves neither a row nor a moved leaf behind; the sibling index is claimed at the insert rather than at the build, so a review left open cannot reserve a slot. A retry prepares before it moves the leaf to the parent, so the reply being re-rolled stays on screen while the reader is deciding about it. A continue prepares before `startStream`, so no bubble fills in behind a request that is still a question. The composer is told when the send COMMITS rather than when it is asked for (`sendMessage`'s `onCommit` → `InputArea.releaseDraft`): with the gate disarmed those are the same tick and the box empties on the press exactly as it always has, and with it armed the draft and its attachments are still sitting there if the review is cancelled. What an edited prompt does NOT change is the story: the turn is stored as the reader typed it, because the prompt is a flattened assembly and there is no honest way back from an edited line to the row it came from. The review says so in a line of its own.

**A chat nobody has written in is a MIRROR of the card, not a copy of it.** Its rows hold the character's First Message and alternate greetings and nothing else, so an edit to the card reaches them: `serverDb.updateLibraryEntry` calls `refreshSeededGreetings` on every save, so no caller reimplements the rule. Without it every unstarted chat quietly opens on a version of the character that no longer exists anywhere. The moment the chat holds something the user put there (a turn, a reply, a hand-edited greeting, an extra opening written by hand, a generated opening scene), it is a story, and the card stops reaching it.

**Recognition asks the CHAT, never the card's history.** Every seeding path records what the card handed over: `chats.seeded_greetings`, a JSON array, written by `chatStore.seedCharacterGreetings` and the refresh itself, and read by nothing else (which is why `mapChat` deliberately does not carry it and no client type mentions it). A chat qualifies when its rows are **exactly that list**: same count, same order, every row still an unedited root-level assistant turn with no attachment. NULL means no claim was ever made (imported chats, and every chat older than the column), and those never follow the card. **This is not the same as matching against the greetings a save happens to be replacing**, which is the obvious shortcut and is wrong: a chat holding a story while the card moves on ends up holding a text the card no longer recognises, so emptying it back down could never hand it back, and whether an emptied chat followed the card came to depend on invisible history. From outside that reads as random, which is worse than either answer.

**There is deliberately no "this chat has been used" flag.** The claim is provenance (this text came from the card), not history (this chat was played), and the difference decides the behaviour: an emptied chat follows the card again, because nothing left in it is the user's to protect. The exact match is the whole safety net: a single character the user typed anywhere in the chat breaks it, so a hand-edited greeting or an opening written by hand is never overwritten. Scope is the variant that actually changed: chats pinned elsewhere keep what they were pinned to, and a save that MOVES the active version pointer (a fork, a switch) is not a content edit at all and reconciles nothing. The rewrite is in place (row ids survive, so a reader parked on the third greeting stays on it), stamps no `edited_at` (the card wrote it, not the user; that stamp is memory's staleness signal, architecture/memory.md), leaves `chats.updated_at` alone so the chat list can't reshuffle under the cursor, and retreats the leaf to the First Message when the greeting it was on is dropped. A card that gains its first opening seeds an empty chat (which is why the claim is written even when the character has no greetings at all: an empty claim is still a claim), and a card that loses every opening empties one and nulls its pointers. **A generated opening scene ends the mirror and costs nothing to support**: the candidate query counts rows, so the extra root makes `row_count !== claimed.length` and the chat is skipped before a single row is read. The claim itself is never rewritten by a generation, so deleting every generated opening leaves the rows exactly equal to it and the mirror resumes on its own. Pinned in [`server/greetingRefresh.test.ts`](../server/greetingRefresh.test.ts) by name, because the rule holding it is a row count and nothing in the SQL says "opening". **A card save that does not touch the opening never looks at a chat**, and the candidate query COUNTS each chat's messages rather than reading them, so a card edit costs nothing on the long stories of that character. Covered by [`server/greetingRefresh.test.ts`](../server/greetingRefresh.test.ts).

**Invariants to keep** (each fixed a real bug, and the steering pair was designed in from the start): a 'once' steering note is spent only after a story generation's PERSISTED success (send/regenerate/continue/opening scene), and **the spend belongs to whoever does the persisting**. For a reply and an opening scene that is the server, inside the same transaction as the row (`commitGeneratedTurn`), and it has to be: the page that asked for the turn may never come back, and a note left armed by its absence applies itself to the next generation as well, which is the exact double-apply this rule exists to prevent. Those two carry the **ids the prompt actually resolved** (`BuiltPrompt.oneShotSteering`, taken from the same rows and the same gate as the stack that was sent), so what a turn spends is what a turn sent, and a note edited to permanent while the model was writing is left alone. Continue still persists client-side and so still spends through `messageStore.spendOneShotSteering`: errors, stops that kept nothing, and continue's no-new-content soft returns never spend, so a failed steered turn keeps its guidance for the retry, while a stop whose partial text WAS persisted spends like any other landed turn (the guidance already shaped text now in the story; carrying it forward would apply it twice); and every build site calls `steeringStore.flush()` before `buildPromptMessages`, so a note typed inside the debounce window can never miss its own send (the builder reads the db rows, not the store's optimistic copy); the three story paths get it from `prepare`, and the opening scene, which has no hold, still does it by hand. The originals: persona is locked per user message at send time (`personaId`), and the one deliberate after-the-fact rebind is the composer menu's "Relabel your messages…" (`messageStore.setChatPersona` → `db.setChatUserPersona`, scope `messages`), which re-attributes EVERY user turn in a chat at once so imported/legacy chats stop rendering a plain "You"; character version is NOT locked per turn: it is per chat, and repinning applies to everything the chat does from then on (architecture/library.md); sibling indexes are never reused within a parent: merging sibling sets appends after `getNextSiblingIndex`, which is asked per CHAT and not per parent id alone, since every chat's roots carry the same NULL parent and an unscoped query would number a new chat's first root off the highest root anywhere in the install (pinned by [`server/siblingIndex.test.ts`](../server/siblingIndex.test.ts)); edits of memory-archived turns drop the summary covering them (see architecture/memory.md; the archive boundary is derived, so nothing else has to move); and **no chat pointer may name a deleted row**: the leaf and the canon marker retreat to the nearest surviving ancestor, the root recomputes from surviving parentless rows. That last one is the db's own guarantee (`repairChatPointers`, architecture/server-core.md), so every delete door inherits it; this store's `repairCanon` and its leaf re-homing are the POLICY on top (which sibling the reader lands on for continuity), and they write after the delete, not instead of it.

**Pure helpers**: [`message-tree.ts`](../src/lib/utils/message-tree.ts) owns active-path walks, role-agnostic sibling resolution, subtree capture, deletion blast radii and navigation. See [`swipes.md`](swipes.md) for swipe generation and replacement semantics.

**A chat's depth is user data, so nothing that walks the tree may recurse, and nothing may re-seat an array per turn.** A chat is a parent-chain: depth is the length of the conversation and grows without bound, so a recursive walk turns story length into stack depth and a long enough story throws `RangeError` instead of drawing. It fails in the worst possible shape too, because the engine's ceiling moves with JIT state and differs by several times between V8 and JSC, so the same chat can work on one page load, on one browser, and not the next. The quadratic half is quieter and reaches the same place: an `unshift` or a `splice` per turn makes opening a chat cost the square of its length. The message-tree module states the rule in its header and is held by a case at 100,000 turns in its test file (far past what any engine allows a recursive walk, so no recursive implementation can pass on any runtime), and **a new walk over the message tree gets the same case**, or the rule holds only where somebody remembered it. The server already lives by this: `hashChatTree` and every subtree delete are iterative or recursive-CTE, never recursive JS.

**A transcript that will not load must say so and stay retryable.** `selectChat` claims `activeChatId` before awaiting `loadChatState`, so a failed load would otherwise leave the store naming a chat whose state never arrived, and the "already open" guard at the top then reads that pair as a no-op and swallows every retry: the row goes dead until a page reload, with nothing on screen saying why. So the load is wrapped: the previous chat id is restored, the welcome screen comes back if that is where the reader was, the failure is toasted through the shared `toastStore.failed` door, and the error is rethrown. Nothing here is specific to any one cause of failure, which is the point; it is what keeps the next one visible.

**Satellites**: [`chatCast.svelte.ts`](../src/lib/stores/chatCast.svelte.ts): lightweight chatId→characterId and chatId→last-persona indexes for chat lists (names/art resolved lazily against the library); [`inputDraft.svelte.ts`](../src/lib/stores/inputDraft.svelte.ts): per-chat composer drafts, debounced 500ms per chat on the shared `DebouncedWriter` (which commits them when the tab goes away), synced across devices; [`inputHistory.svelte.ts`](../src/lib/stores/inputHistory.svelte.ts): the ↑/↓ recall log, deliberately independent of the messages table; [`branch-labels.ts`](../src/lib/utils/branch-labels.ts): the fixed branch color palette (palette keys stored, not CSS values).

**Components** (`src/lib/components/chat/`, `sidebar/`): presentation over the two stores. `ChatContainer`/`MessageList`/`Message` (render + per-message actions calling `messageStore`), `InputArea` (composer: drafts, history recall, attachments, the **Steering popover** (compass button in the feature row, hidden while the engine is off, accent-tinted with a dot while any note is active, deliberately enabled mid-stream since steering is next-turn state). InputArea owns only the trigger, its dot and the commit-and-flush-on-close (`SteeringPopover.commitQuick()` for the quick box's component state, then `steeringStore.flush()` for the note editor's debounce, so no outside interaction can build a prompt against guidance the user typed but never got to commit); the panel itself is [`SteeringPopover.svelte`](../src/lib/components/chat/SteeringPopover.svelte), a complete two-view surface (the stack of scoped notes with per-note switches, and the shared note editor) documented in architecture/engines.md. InputArea also hands it that close callback, so its Manage link can put the popover away before raising a panel that covers the whole composer. The chat meter passes the resolved note list into `assemblePrompt` through the same pure resolver and gate as prompt-builder (architecture/prompt-pipeline.md coupling 8), and it prices `pricedPath` (the active path plus an EMPTY synthetic user turn), never `activePath` itself: a send inserts the user's turn first, so the resting path is one turn short of what the send injects. The placeholder stays empty because the draft's own tokens are the meter's separate "your message" number. The **setup chip** ([`ChatSetupChip.svelte`](../src/lib/components/chat/ChatSetupChip.svelte), feature row, standing whenever a chat is open): the one place a story claims anything, and the one readout of what it is running on (the persona and the short model name). It opens on a summary of one row per category (Persona, Preset, Connection, Version, Lorebooks), and a row drills IN PLACE into that category's own list, which is where the pick is made and where the way back to the app is pinned; every pick writes only this chat (architecture/ui-shell-settings.md, "A chat claims what it can name", which owns the two-level shape, the face grid and the lorebook row's toggles). The first four run in the order a prompt happens in: who is speaking, what builds it, where it is sent, and last the character variant it is played against, which hides itself on an unversioned character. **Lorebooks trail all of them**, because that row adds to what the story already has rather than replacing an answer, and it hides itself on an empty shelf for the reason the Version row hides itself. Which persona a chat is played by therefore comes from `chatPersonaEntry` and not from the app pointer: new user turns are stamped with it (`createMessage`), prompt assembly speaks as it, the transcript expands `{{user}}` to it, and turns already sent keep theirs. Deliberately NOT the same thing as the hamburger's "Relabel your messages…" (`ChatPersonaDialog` → `messageStore.setChatPersona`), which re-attributes a chat's existing user turns and claims nothing; the two must stay separate entries. **Their names share no word**, which is the rule to keep rather than the particular wording: the two sit centimetres apart in the same composer, both open a list of the same personas with a mark on the current one, and a reader has nothing but the label to tell them apart. So the chip's row is named for the thing being chosen (`Persona`, the same word the character editor's New Chat Defaults row uses for the same choice) and the dialog is named for the act only it performs (`Relabel your messages…`). Its prose still says "persona", because that is what it is relabelling to, and prose is not what a reader picks a control by. The **Spellcheck / Impersonate** hamburger entries (gated by their switches, disabled on an empty draft, mid-stream, or while one is already open) raise [`TransformPanel.svelte`](../src/lib/components/chat/TransformPanel.svelte): a strip mounted **in flow above the composer**, never a modal, so it shortens the transcript instead of covering the story and the draft it rewrites stays on screen underneath it. It runs `composerTransformService` itself (abortable; errors render in the strip), and its four phases exist to keep every call behind a press: `setup` (nothing spent yet: the price of the run counted through the service's own `buildComposerTransformPrompt`, so the estimate can't drift from the request), `running`, `ready`, `error`, with Stop landing back in `setup` rather than on a dead surface. **Impersonate runs only on Ghostwrite**: narrative person and style are written in its own prompt, with no perspective selector or per-chat choice. The rewrite button requests another take using that same prompt. Spellcheck opens straight into `running` because it has nothing to choose, which makes its menu row the press. **The proposal is read differently per kind**: Spellcheck as an inline word-diff redline (`utils/text-diff.ts`), Impersonate as the message itself, since a word diff between a one-line note and the message grown from it is an unreadable weave of accidental matches rather than a review. Approve replaces the draft only after recording the original into input history, and close/Escape/error leave the composer byte-for-byte untouched; **the composer is frozen while the strip is open** (textarea and Send disabled), because the proposal is against the draft as it stood at the press and approving over an edited box would throw that edit away silently. Escape closes the strip and is marked consumed, per the shell Esc contract. InputArea's own token-breakdown popup is portaled to `<body>` at z 1000: it must stay above the chat column's stacking context). **Continue and Retry belong to the turn, not to the composer.** Both act on the reply that was just read, so both are buttons on that reply's own action bar (`MessageActions`) and neither has a row in the composer menu: a menu press to reach an act whose subject is on screen is one press too many, and Retry was already sitting there under the reply while its twin was two centimetres away behind a hamburger. They are drawn side by side, Retry then Continue, because after a reply the two questions are the same shape: again, or more. Continue draws `feather`, and that is the glyph `/continue` and the prompt hold's Continue gate both source from (`config/prompt-hold.ts`). Deliberately not the forward arrow, which reads right for the act and is already the composer's Send: the hold gates list Send and Continue as two rows of five, and a glyph shared between them is the one thing the eye cannot use to tell those rows apart. Their gates differ by exactly one turn. `showRegenerate` refuses a seeded greeting, which has no prompt behind it to re-roll, while `showContinue` takes one, since a continuation works from the reply's own text; both ride `isLast` and are disabled while generation is busy. The swipe pager remains visible on the newest assistant response. `Message` calls `messageStore.continueMessage()` directly with the `.catch` toast the opening-scene call site carries: the store toasts every generation failure itself, so only its no-active-chat guard can reach a caller. It is deliberately NOT a bound row in the shortcut registry: Enter belongs to whatever box has focus, so a window-level match would also fire from a rename field or dialog. The registry still carries it as a documentation row, or it would be a key nothing on screen mentions (architecture/ui-shell-settings.md). **What it does follows the last turn**: a reply gets re-rolled, a user turn gets the reply it doesn't have yet, and one `regenerateLastResponse('replace')` covers both, because `'replace'` on a user turn finds nothing below to delete and goes straight to generating. Regenerate replaces all existing swipes only after the new response has been saved successfully; see swipes.md. `canContinue`, `canRegenerateLast` and `regenerateLastHint` stay on `InputArea` as the gates for that key and for `/continue`, `/retry` and `/swipe`; the buttons spell the same predicates locally against `isLast`, and the store's own leaf check sits under all of them as the one that decides. **New chat** sits directly under Chats at the top of the menu, one `chatStore.createChat` call against the open story's own character: it is the Chats panel's New Chat button reached without opening the panel, and it stays a single store call so the creation recipe (title, version pin, seeded greetings, opening the result) is never reimplemented here. Its two gates differ in kind on purpose. Mid-generation it warns through `messageStore.warnIfBusy()` instead of being disabled: creating and seeding another chat still requires an idle mutation state, unlike Home's view-only navigation; the Chats panel's own button carries the identical guard on its direct-create branch, so neither door drops the reader into a chat while a reply is still landing in the one behind them. What that reply does in the meantime is the stream-ownership rule above, not this guard's job. It IS disabled, with the tooltip saying why, when the chat's character no longer resolves in the library (the row reuses InputArea's `activeCharacterEntry` derived): a chat orphaned by a character deletion would otherwise mint one carrying a dangling character id, no greeting and a date-only title. Every hamburger row is icon + label on the one scoped `.composer-menu-item` recipe, and those icons are **sourced, not chosen**: Spellcheck wears its `registry.ts` icon (`checkCircle`, see architecture/engines.md); Impersonate uses its `mask` icon on the composer toolbar immediately after Steering, New chat wears `plus` because that is what the Chats panel's own button draws, and the two Insert rows wear the role glyphs `MessageAvatar` draws for a portrait-less turn (`user` / `sparkles`), so a row reads the same in the menu as the thing it makes. Relabel is the one row with nothing to source from, since no other control does what it does, and it wears `tag` for the verb rather than anything built on `user`: Insert user message already holds that glyph, and two person marks in one short menu is a difference the eye has to read the labels to find. The **attach** button beside that hamburger is a menu on the identical recipe (same `.composer-dropdown` shell and `min-w`, same `.composer-menu-item` rows) rather than a direct file-picker trigger, and it wears `paperclip` rather than `image`: attaching is the concept, images are only the first attachable kind, and the toolbar shouldn't have to re-teach that button when the second one lands. Its `<input type="file">` deliberately lives **outside** the `{#if}`: picking the row closes the menu, and an input that unmounts in the same tick never gets to open its dialog. The composer is also a **drop target**, and for pictures only: a story turn has nowhere to put a text file, so one dropped here is refused **by name** rather than ignored, since a silent drop reads as the gesture having failed. The overlay that appears while a drag is over the composer is `pointer-events: none`. The drop is handled by the shell underneath, and an overlay that became the event target would swallow it. `BranchNavigator` (sibling swipes), `ChatsView` + `ChatListRow` + `ChatsView` + `DuplicateChatDialog` (the chats browser, raised from the composer hamburger's "Chats" (its only entry point from inside a story, there is no TitleBar button) and from the welcome landing; two scopes the header's own switch picks between: scoped to a character it lists that character's chats and New chat creates another one directly, scoped to everything it lists **every** chat and the button hands off to the flow in architecture/ui-shell-settings.md. See the "Chats panel" section below). See the "Chats panel" section below for what the rows say and where the numbers come from. **Continue streaming** rides the same `chatStore.stream` record plus its `continuingMessageId`: while it is set, `MessageList` suppresses the `StreamingIndicator` bubble and instead hands the target `Message` a `streamTail`/`streamTailThinking` pair: the bubble renders `previewContinuation(stored, tail, anchor)` through the normal display pipeline (so display regex and self-refs apply to the seam too), where the anchor is the content with self-refs expanded and the rule is the final join's glue seam plus a hold on tails that are still pure restatement, so a model re-typing the message never paints it duplicating itself on screen; new reasoning streams into `MessageReasoning` after the stored block with the pulse marker. `endStream()` drops the whole record, so the id can never outlive its stream, and the persisted join happens only in the store. The component never writes. Display-scope regex rules (architecture/prompt-pipeline.md "Regex rules") are applied at render time in exactly two places (`Message` and `StreamingIndicator` run content through `regexRulesStore.forDisplay(content, role, depth, preset)` before `renderMarkdown`, each resolving that preset ONCE into its own `$derived` rather than inside the html: both recompute per streamed token, and resolving a preset parses the chat's feature-state blob), never at save time: Copy, the editor, and the stored rows always carry the original text, and the streaming token estimate deliberately counts the raw stream. **`depth` is counted by `MessageList`, not by the row**: `messages.length - 1 - index`, plus one while a fresh reply streams into its own bubble, because that bubble is a turn the stored rows don't have yet and without the offset the newest reply would flip between turn 0 and turn 1 as the stream settles. A continue writes into a row that already exists and so adds no turn; `StreamingIndicator` passes 0 outright, which is the same number the row it becomes is handed. `Message` then runs the result through `expandSelfRefs` (the chat's persona + its bound character) so raw `{{char}}`/`{{user}}` in stored content resolve live on screen. This must stay in lockstep with the generation-side expansion in `prompt-assembly.toInjectedMessage` (coupling #5). **The story text is patched into the page, not reprinted onto it.** Every transcript surface that renders model output (`Message`, `StreamingIndicator` and `MessageReasoning`) hands its HTML to the [`renderedHtml`](../src/lib/actions/renderedHtml.ts) action instead of `{@html}`, and the difference only matters while a reply is arriving, which is to say constantly. `{@html}` applies a new string by throwing the whole subtree away and building a fresh one, and everything the reader is doing inside that subtree lives on the nodes it destroys: a folding panel loses the `open` they just clicked, a text selection collapses, and worst of all the click usually never lands, because a click fires on the common ancestor of where the press went down and where it came up and a panel replaced between the two hands the event to the container instead. The action parses the new HTML into an inert `<template>` and reconciles it against what is on screen, positionally: there are no keys to be had in rendered markdown, and position is the right match anyway, since a reply grows at its end and everything above that end lines up and survives. Two rules hold it together: the HTML is trusted to have come from `renderMarkdown` and nothing there relaxes that, and **`open` on a `<details>` is never synced**, because it is the reader's state and not the text's: a panel that survives a patch keeps what they set, while one that arrives fresh is built from the source node and so still honours whatever the reply asked for.

**Transcript edge navigation.** `MessageList` keeps the first-message button at the upper right and the latest-message button at the lower right. Both buttons stay hidden at the latest edge and appear when the reader scrolls back; the first-message button also hides at the start of the full path. Visibility follows the measured scroll edges, independently of generation and the wider near-bottom band used for stream pinning; resize observers cover both the viewport and transcript content. First reveals the path from index zero before scrolling, including in manual paging mode, and releases the stream pin. Latest resumes following. Explicit jumps invalidate pending earlier-page position corrections and automatic fill snaps, so those older callbacks cannot overwrite the destination. Deliberate travel respects the app and OS reduced-motion preferences.

**The message cursor is where the keyboard is in the story.** The transcript is long and Tab is not navigation, so a turn a hundred messages back has to be ADDRESSED rather than stepped to. [`chatCursor.svelte.ts`](../src/lib/stores/chatCursor.svelte.ts) is the one thing the doors share, and it holds one turn id stamped with the chat it was set in, so a cursor reads as absent in every other story and a chat switch drops it with nothing to clean up. **Marking and taking are separate facts** and the split is what makes find-in-chat work: `mark` says which turn the cursor is on and paints the ring, `goTo` also moves the keyboard, and the search bar marks every hit while the reader is still typing in its own field, where a mark that took focus would empty that box on the first match. Three doors reach it and they are the three distances: **stepping** for the near turn (⌥↑/↓ from anywhere, bare ↑/↓ once the keyboard is on a card, and ↓ past the newest hands it back to the composer, which is what makes the transcript and the box one continuous run rather than two places with a wall between), **find in chat** for anywhere in the branch (its ring is temporary: closing by X, Escape or another unmount clears the search-owned mark, keeps the reading position and does not focus a message or reopen the mobile keyboard; a query with no hit also clears its old mark), and **`/go <n>`** for the address, the number every turn already wears under its portrait. Escape from a turn goes back to the composer through the shell's own Escape ladder (architecture/ui-shell-settings.md), so the cursor needs no exit of its own. **Stepping is always a step, never a resume**, which is what lets one gesture both enter the story and walk it: the shape a reader reaches for is the modifier held down and the arrow tapped, so a door that resumed would answer the second tap by landing where it already was, and a key that lands where it already was reads as a dead key. **The cursor IS focus on the row**, which is the whole reason its keys can be bare letters: on a turn the keyboard sits on a card and never in a box that takes text, so nothing has to be modified to stay out of the way of typing. `Message.svelte` therefore gives the row `tabindex="-1"` (focusable, deliberately not in the tab order, since tabbing through a long transcript is not navigation), and handles the keys **only while the cursor is on that turn and the event's target is the row itself**: everything inside owns its own keys, and one of their events passing through on the way up is not this turn being addressed. **A pointer press is not one of the doors.** Clicking anywhere in a card focuses the row as well, since the browser hands focus to the nearest focusable ancestor of what was clicked, and marking from that would leave a ring on the last turn a reader touched with nothing to clear it: the ring says where the keyboard is, which is a claim a click never makes. So the row marks from its own `focus` event only while the browser reports that focus as keyboard-driven (`:focus-visible`, which never matches a click or a tap), and that one condition is also what lets the two generic keyboard doors land a cursor without knowing anything about turns, since both only focus the row: the hint labels and the focus keys (architecture/ui-shell-settings.md). The three doors above mark in the store before they focus anything, so none of them depends on it. The keys follow the ring rather than focus for the same reason: a bare `E` opening an editor on a card wearing no ring would be a key landing where nothing on screen says it lands. Every one of those keys is that row's own button and never a second path to the act, so `Delete` and `R` open the very menus the pointer opens and the confirmations gating them hold for the keyboard exactly as they do for a click. **Adding a key there adds a row to the `turns` group** in `commands/shortcuts.svelte.ts`, or it is a key nothing on screen ever mentions. `MessageList` owns the landing, and it is the same reach as the arrival mark with a different ending: a turn behind the transcript window is loaded back in first and the effect re-runs on the row that now exists, the scroll says `'instant'` (coupling 15; stepping through a stretch of story would otherwise queue one animation per press) and deliberately does not arm `programmaticScroll`, since landing mid-history SHOULD release the bottom pin. The ring rides `.message-bubble-shell::before` like the card outline, so it works in every chat style and the card's geometry is identical whether or not the cursor is on it; it follows the style blocks so the outline keeps each style's card geometry, including Manuscript's full-width, evenly rounded card. It is dimmed while the keyboard is elsewhere and bright while the row has focus, because "where Alt+↑ comes back to" and "your keys land here" are different claims. The row also carries `data-hint`, which is what lets the hint labels reach a visible turn directly (architecture/ui-shell-settings.md).

**Commands are the composer's other mode.** Typing `/` into an EMPTY composer arms it: the shell takes the accent border and a palette opens above the box, and from there the composer is filling in a call rather than holding a message. [`commands/registry.ts`](../src/lib/commands/registry.ts) is the single list **and** the single parser, one file for the reason `macros.ts` is one: a command is declared, documented, gated and matched in exactly one place. The grammar is the whole design and it is deliberately tiny: a slash, a name up to the first space, and everything after that space as ONE verbatim argument. That is what leaves an argument with nothing to quote and nothing to escape, which is the tax a command language charges on every one-liner the moment it grows separators, variables and closures. So there are none: no chaining, no second argument, and anything that would need one gets a picker or stays a control. **Arming on an EMPTY composer is what keeps prose out of the mode**: a story line containing a slash never enters it, Escape leaves it with the text intact (consumed per the shell Esc contract, so backing out of the palette cannot also close a panel behind it), and a line naming no command closes the palette by itself so Enter sends it like any other message. There is no dead state to escape from, which is why the mode needs no exit affordance of its own. Empty means the whole composer and not just the text box: **a pending attachment blocks arming**, because `/say` writes a turn through `insertDummyMessage` and would land it with the picture still sitting behind it, silently dropped. **A command line is also not a draft** and is never persisted: drafts sync across devices and restore as ordinary text, so a command typed and abandoned would come back as a message that sends itself on the next Enter. Leaving the mode by Escape saves it, because from that press on the line really is prose and nothing else fires (leaving a mode is not an input event). **The Send button answers the same question Enter does** (`commandReady`), so it goes dead over a name still being typed, a refused command or a missing argument instead of looking live over a press that would do nothing; it is also what makes the mode work on touch, where Enter is a newline. **The list is ranked rather than filtered, and headings are for browsing only.** Matching reads descriptions as well as names, so someone who knows what they want but not what it is called still finds it, and that is precisely what makes the ranking load-bearing: descriptions are full of the words other commands are NAMED after, so a flat match puts a command the user is not spelling above the one they are. Spelling the name beats spelling part of it, which beats hitting a description, and registry order decides inside a tier. Group headings therefore appear only on a bare `/`, where the list IS the whole vocabulary: applied to a ranked list they reorder it back into registry order and put the best match under a heading below a worse one, with the highlight sitting on a row that is not the first on screen. **No command implements behaviour**: every `run` is one call into a store or into the composer's own door (`CommandHost`, which carries the three the composer owns rather than a store: Continue and Retry, wrapped differently by `ChatContainer`, and Duplicate, which raises a dialog), so a command and the control it stands in for are the same call and not a second copy of it. **The mode ends on the press, never on the work**: `runCommand` reports one thing, whether the command was accepted, and both refusals it can give (an unavailable gate, a missing required argument) are settled before any work starts, so the composer can empty the line and put the palette away on the spot. What `run` does from there is the command's own business and is deliberately not waited on: a `run` can be a whole generation (`/continue`), and a composer that waited would sit locked around a half-typed `/conti` with the palette still listing matches for the length of it, which reads as a press that never landed. A refusal leaves the line alone, since the text is the fastest way to fix it; a throw inside a command that did start is a failure rather than a refusal and says so itself. **The gates are handed in, never recomputed**: `canContinue`, `canRegenerateLast` and the resolvable character reach the registry through `CommandContext` as the very deriveds the composer's own keys and rows read, which is what stops a command from ever being more permissive than the control it stands in for; a row that cannot run stays on screen and says why in place of its description, since a command vanishing from the list reads as a typo rather than as a refusal. `/retry` and `/swipe` are the two rows behind the transcript's one Retry button and are drawn alike to say so: same call, `'replace'` against `'branch'`. Their gates differ by exactly the one exclusion `'replace'` earns, though, and `canSwipeLast` is a SEPARATE derived for that reason: Retry refuses a user turn that already holds replies because replacing there is a subtree delete, while that is precisely the turn swipe exists for. Two commands cannot reach their target directly and both use a one-shot handoff: `/branch` sets `messageStore.branchTargetId`, which the newest turn's own row claims to open its editor in Branch mode (the editor is that row's state, so the composer may ask for it and nothing more; a row **already editing refuses out loud**, since the composer stays typeable during an edit and flipping an open editor's mode would silently turn a rewrite into a fork), and `/duplicate` mounts the Chats panel's own `DuplicateChatDialog`, so the one question a copy cannot answer for itself is asked here too. Whether there is a question at all is `duplicateAsksAboutMemory` in [`types/chat.ts`](../src/lib/types/chat.ts), read by both doors: two spellings of that rule end with one door asking and the other quietly deciding. This door differs from the panel in exactly one deliberate way: it lands you IN the copy, because the command was typed from inside the story and that is where the next turn goes. The list itself is [`CommandPalette.svelte`](../src/lib/components/chat/CommandPalette.svelte), a presentation surface holding no mode state and resolving no gate (both belong to the box being typed into); what it owns is the one thing a list must get right alone, keeping the moving highlight in view. Coverage is the contracts net alone (`contracts.test.ts`, "commands", architecture/testing.md); the mode's own behaviour is manually tested like the rest of the composer.

**A reply can also contain folding panels of story state.** Presets instruct the model to print `<details>`/`<summary>` blocks and carry regex rules that style them, so `renderMarkdown` allows those tags (plus `div`/`b`/`i`/`u`/`font`) and the disclosure is native: no script, no component, nothing to hydrate. **Their bodies are markdown**, which takes one correction to be true: CommonMark reads `<details>` as opening a raw-HTML block that runs to the next blank line, and a model writes the body on the line straight after `</summary>`, so without help the whole panel arrives as one run-on line of literal text with its list dashes intact. [`model-markup.ts`](../src/lib/utils/model-markup.ts) inserts the blank line that closes the raw block (after `</summary>`, before `</details>`, at every nesting depth, never inside a fence) and drops a `<br>` sitting at the end of a line, which is what the line ending already means once the body is markdown and which would otherwise double every gap in a hand-written or imported panel. That one has no exception: a `<br>` alone on its line empties the line, which is the blank one its author was drawing, while a `<br>` mid-line is left alone because nothing else is doing its job. Inline formatting is validated by [`inline-decoration.ts`](../src/lib/utils/inline-decoration.ts): typography, nonnegative spacing, borders, corners, solid backgrounds and bounded gradients are allowed; positioning, dimensions, layout modes and external resources remain blocked. Font sizes use an absolute 8–64px clamp so nested relative sizes cannot grow without bound. The complete supported properties and ranges are documented in architecture/sillytavern-interchange.md. `.prose details` supplies the default dark surface, accent title/bar and centred SVG chevron; a summary keeps a reserved icon slot even when a preset customizes its padding. Existing messages can gain formatting previously stripped, but stored text and prompt construction do not change.

**Two separate things have to go right for a preset's colour to reach the page, and each of them fails silently on its own.** The first is that the attribute has to survive sanitizing at all: `ALLOWED_ATTR` decides which attributes may EXIST, but DOMPurify then matches the VALUE of anything it does not hold to be inert against `ALLOWED_URI_REGEXP` and drops the attribute when it fails. Its inert list is fixed and contains `style` and `class` but **not** `color`, so a hex colour is read as a URL, fails the deliberately narrow `https?|mailto` pattern, and `<font color>` is deleted before any stylesheet sees it. `ADD_URI_SAFE_ATTR: ['color']` is what says a colour is a colour; the `afterSanitizeAttributes` hook remains the thing that decides whether it is a colour we accept. `target` and `rel` sit in `ALLOWED_ATTR` under the identical trap and would not survive either: nothing emits them, which is the only reason it does not matter. Adding an attribute to that list is therefore never one edit: ask what its value looks like to a URL matcher.

The second is the cascade, and it has to be said out loud in CSS because it says the opposite of what you want. A `<font color>` is a presentational hint, which ranks **below every author rule**, so the quote tint on the `.quoted-text` span **inside** it takes the colour straight back, and coloured dialogue is exactly that shape, `<font color="…">"the line"</font>`, a colour wrapped around a quoted line. It is the thing presets most want, and the tint would take it back from every one of them. One rule in `app.css` hands quote, strong and emphasis back to `inherit` under anything carrying a colour, because a preset that colours a run means the run. It matches **the elements themselves** (`font[color]`, and a `style` whose serialized declarations begin with or contain `color:`) rather than a marker attribute written during sanitizing: the colour is already in the DOM by then, so nothing outside that stylesheet has to cooperate for the rule to hold. The price is a coupling to how `sanitizeDecorations` serializes (`property: value`, joined by `'; '`), which is what lets the selector anchor tightly enough that `background-color:` is not read as a text colour; `inline-decoration.test.ts` pins that shape with the stylesheet named in the test. **The editor has no save-time menu.** `MessageEditor` takes a `mode` (`save_only` | `create_branch`) decided by the button that opened it (**Edit** rewrites this turn, **Branch** creates and opens a separate chat with the ancestry through this turn, using the edited text only for the copied endpoint), and Save just saves. Three things follow. **One**: nothing is created until Save, so cancelling a Branch costs nothing. An in-place save of untouched text closes without writing; a Branch of untouched text still forks, because a verbatim alternate is a legitimate place to write into later. **Two**: `EditAction` has exactly two values. There is deliberately no "rewrite in place and delete every descendant" third one: that is a subtree delete hidden behind a Save button, and a Branch reaches the same outcome without destroying the timeline it forks from. **Three**: `create_branch` does NOT auto-generate on a user turn. The copied turn becomes the new chat's leaf, which puts Generate one click away on its own toolbar, deliberate breathing room rather than a call the user never asked to spend. **An in-place save over a folded turn asks first.** A rewrite outdates the summary covering that turn, which the engine then discards and re-reads (architecture/memory.md), so Save on an archived message raises a confirmation inside the editor: the draft stays on screen above it, Keep editing returns to it untouched, and the panel states the real numbers from `memoryStore.impactOf` (which summary goes, how many pause behind it, how many turns are re-read and what triggers that). It is raised at Save rather than at the Edit button because opening an editor costs nothing and the price has to be readable beside the text it is being paid for; `create_branch` never raises it, since a branch copies into a new chat and leaves the folded turn alone. The panel offers **three doors, and the gesture separates them**: press-and-hold buys the re-read, a plain tap saves as a MINOR edit that costs nothing and leaves every summary standing (`editMessage(…, { minor: true })`, memory.md coupling 8), and Keep editing returns to the draft. The minor door is not an optimisation the app may apply on its own: no diff of two strings tells a typo from a retcon, so it is only ever the user's own answer to "does this turn still say the same thing". While the confirmation is up the editor is `locked`: it holds a SNAPSHOT of the draft, so a keystroke landing after it would be silently discarded by the commit. **Branch is offered on every message**, both roles: a user turn forks into a different thing said, a reply into a hand-written alternate to swipe between (the clone is always the same role, so this cannot mint a mixed sibling set, see coupling 1). **The transcript is the only place either button exists.** In the Portraits chat style the message card is a two-column flex row whose portrait column is `position: sticky` against the list scrollport. This requires `overflow: visible` on the card and **no vertical padding on the `.message-list` scroller itself** (a scroll container's own padding insets the sticky constraint rect; the spacing lives on `.message-list-content`). That same `.message-list-content` is also the transcript's width: it centers at `--chat-content-max` inside the chat column, which above the dock breakpoint is a share of the screen rather than a fixed width (architecture/ui-shell-settings.md coupling 7), and the cap must stay on this content box: Portraits and Manuscript rows fill their row, so uncapped they stretch to whatever the share resolves to on a wide screen. `InputArea .input-inner` carries the same cap so the composer sits exactly over the text it feeds. `MessageList` autoscroll pins to the bottom only while the user is near it (~120px); any deliberate **upward** scroll releases the pin at once (direction-tracked against `lastScrollTop`, with a `programmaticScroll` guard so the auto-follow's own snap isn't read as intent), so a fast stream can't yank the view back mid-read; a floating "jump to latest" pill (with a "New" hint for unseen messages) restores it. That guard spends itself on ONE scroll event, which pins two rules to `snapToBottom`. It is armed **only when the snap will actually move the scroller**: a write to a scroller already at the bottom (the normal case while following a stream) fires no scroll event at all, so the guard would stay armed and swallow the user's next real scroll-up, leaving the pin set and the next token free to drag them back down. And the follow scrolls with `behavior: 'instant'`, overriding the scroller's CSS `scroll-behavior: smooth`: an animated snap fires a whole run of scroll events and only the first is covered, so the rest read as the user scrolling mid-glide. `jumpToLatest` passes `'smooth'` because that one IS a deliberate travel across a long distance. **The streaming→settled transition never snaps** (`streamSettled`): the settled turn replaces the streaming bubble in place, so a pinned reader is already at the bottom and one who scrolled up to read must not be thrown to the end by the last frame of a reply they already left behind. Auto-scroll fires only for path **extensions** (the previous leaf is still on the new path: a send/reply/dummy append) and chat opens, and "which chat" is asked of the rendered path rather than of `chatStore.activeChatId`, which names the chat being opened a flush before its rows arrive: keyed to that id the swap reads as a chat change against the PREVIOUS story's rows, and the new story's rows then read as a branch switch, the one case that deliberately does not scroll, so a chat would open wherever the last one's offset happened to survive; a path switch that replaces the tail (swipe, branch jump, delete re-homing) asks the pin **as it stood before the swap**, because that pin is part of the reading position and the effect still sees it (it runs before any scroll event the swap fires). A reader who had scrolled up keeps their offset with `nearBottom` re-baselined from real geometry, so switching into a long branch never teleports the view to its bottom and the stale pin from a short branch can't make the next stream token do it either; a reader who was AT the bottom stays pinned there, since the turn a swipe replaces is the one they were reading and the arrow they pressed sits at that turn's bottom, so holding their offset would strand them mid-message with the controls off screen. `lastScrollTop` is rewritten on both paths: the swap can shrink the content and let the browser clamp `scrollTop` by itself, and a clamp measured against a stale value reads as the user scrolling up. **What it flashes is the CARD** (`[data-message-card]` on the bubble, resolved from the row's `msg-<id>`), never the row: a row is as wide as the scrollport, so the scroller clips its glow left and right and the following turn paints over the bottom of it, leaving a bar along the top edge and nothing else. The effect reads the path as a dependency so a target named before its branch has rendered still lands, and a target whose row never appears (deleted between the click and the jump) clears itself after a beat instead of waiting to fire under a later, unrelated branch switch. It deliberately does NOT arm `programmaticScroll`: landing mid-history SHOULD release the bottom pin, which is exactly what the resulting scroll events do. `.message-list-wrap` carries `min-width: 0` so a wide expanded thinking block scrolls inside its own panel instead of stretching every row past the viewport. **The transcript is windowed, and nothing else is.** `MessageList` renders the newest `transcriptPageSize` turns of the active path (Settings → App → General, "Long Chats": `generalSettings.transcriptPaging` / `transcriptPageSize` / `transcriptLoadMode`, on by default at 100) and reaches further back on demand. What that buys is not only a faster open: every turn on screen is a markdown parse plus a card of DOM, and the pin-to-bottom logic re-measures the whole scroller on every streaming token, so an unwindowed long branch drags every reply after it too. Three rules hold it together. **The top edge is a pinned TURN, never a count back from the newest one.** A counted window slides forward with the story: every reply that lands pushes a turn off the top, and removing content ABOVE the viewport shifts everything a reader who scrolled back is looking at, on every single turn a long session generates. So the edge is pinned on arrival and from then on only ever moves EARLIER, which makes the whole rule one line: within a visit the loaded stretch only grows, and it grows at the end the reader is already watching. Leaving the chat is what resets it (the anchor is dropped on the way out, or returning to a story would quietly revive the stretch loaded last time while a detour through a third chat would not), and it is keyed to the chat the RENDERED path belongs to, never to `activeChatId`: selecting a chat sets that id and then awaits the load, so for one flush the store names the new story while the old one is still on screen, and an anchor written there would pin the next chat's window onto a turn from the last one. The pin is state rather than an effect that resets on chat change, because an effect runs a frame AFTER the new chat has already mounted, at the previous one's size, which is the exact burst this exists to prevent. The anchor carries its index beside its id, and falls back to it when the turn itself is gone (deleted, or a branch switch replaced that stretch): the index still states how far back the reader had reached, where collapsing to the base window would yank them forward instead. **Every index a message is handed is measured against the whole path**, never against the rendered slice: the `#N` ordinal, the depth a regex rule is scoped by, `isLast` and the memory-ghost prefix all count from the start of the branch, so a window that shifted them would renumber the story and re-scope every depth-bounded rule. **The clip is on rendering alone**: `allMessages` and the active path stay whole, so the tree, prompt assembly, the chats panel and the blast radii never see it. Earlier turns are loaded on demand. The reader's own (`loadEarlier`, from the top-edge button or from scrolling within `LOAD_EARLIER_PX` of the top, whichever `transcriptLoadMode` says) holds the reading position, since the turns arrive ABOVE the viewport. Three things make that correction correct rather than nearly correct, and every one of them is silent when got wrong. It is **measured against a turn**, the first row still on screen, rather than computed from the scroller's total height, which also grows when a reply lands below while the load is in flight (the reader would then be pushed down by a message they were not even looking at). Measuring is also what makes it idempotent with the browser's own scroll anchoring, which does this same job on the engines that have it and is deliberately left ON: whatever it already fixed is not in the number, so the two can never double up, and `overflow-anchor: none` would trade a late-loading image shifting the story on Chrome and Firefox for nothing at all, since Safari has no anchoring and the manual correction is needed regardless. It is written through **`scrollTo` with `behavior: 'instant'`**, which is the ONLY value that overrides this scroller's CSS `scroll-behavior: smooth`: `auto` defers to that CSS, and so does a plain `scrollTop +=`, so either one ANIMATES the correction and the reader watches the entire stretch that just loaded fly past. The button load mode is where that shows, since the reader is parked at the top edge with no gesture of their own to cut the glide short. Every scroll write on this scroller that must land rather than travel takes the same value, find in chat's re-park after a load included. And it is **announced rather than kept private**: `onContentShift` hands the whole travel (ours plus anything anchoring did) up to `ChatContainer`, whose margin-wheel target is an ABSOLUTE scroll position, so a wheel that just reached the top edge would otherwise snap back to where the content used to start and load again on the next notch. Anything else that remembers a scroll offset across a load owes itself the same correction. Find-in-chat's door (`showFrom`, through the `loadThrough` prop) deliberately does not, because the bar parks the view on its own hit afterwards. A third case only looks like a door: an auto-mode window too short to fill the viewport has no scroll for the reader to ride, so it loads until the scroller has something to scroll, and reads its own height as the condition so it settles itself. It stands down on a zero-height scroller, which says nothing about fit and would otherwise load a whole chat with nobody looking, and it re-snaps a pinned reader afterwards, since those turns arrive ABOVE and no message landed to move them: without that the story finally overflows with the reader parked at its top. **Find in chat** ([`ChatSearchBar.svelte`](../src/lib/components/chat/ChatSearchBar.svelte)) is a floating bar `MessageList` mounts inside that same wrap (the scroller is handed to it as a prop, which is why `listElement` is `$state` and not a plain `bind:this` let): open state + query + the Match case / Whole words options live in the satellite store [`chatSearch.svelte.ts`](../src/lib/stores/chatSearch.svelte.ts), deliberately NOT in uiStore's panel choreography, since the bar is inline chat chrome that must be able to sit open beside a docked Settings or Library. It is raised from the composer hamburger ("Find in chat…") and by Ctrl/Cmd+F in `Workspace.handleKeydown`, which takes the key off the browser's find only while a chat is on screen and no overlay covers it. The search runs over the **rendered** transcript, not the stored rows: display regex rules, self-ref expansion and markdown are already applied on screen, so DOM matching is the only way the read text and the searched text agree, and it lets a hit span inline markup. [`utils/chat-search.ts`](../src/lib/utils/chat-search.ts) holds the pure matcher (`buildSearchRegex`, tested in `chat-search.test.ts`: literal escaping restricted to regex syntax characters because every other backslash escape is a SyntaxError under the `u` flag; Unicode letter/number lookarounds instead of ASCII `\b`, which never fires beside `ş` and so would make a whole-word search for "şey" find nothing while matching "eyler" inside "şeyler"; and the dotted/dotless i fold: Unicode pairs only I↔i, so without `[iıIİ]` a search for "kapı" silently misses "KAPI") plus `findMatchRanges`, which joins text nodes **per block** so offsets map straight back onto nodes and "Ali"/"Veli" in adjacent `<li>`s can't read as one word. Hits are DOM Ranges painted through the CSS Custom Highlight API, never `<mark>` injection: the message markup stays untouched, so `renderedHtml`'s ownership of that subtree and Copy are byte-identical. Enter / Shift+Enter cycle, Escape closes and is consumed (shell Esc contract); the match pass writes its cursor under `untrack` so a jump can't re-trigger the DOM walk. Scope is the story text only, and matches are capped at `MAX_MATCHES` with the counter showing "N+" rather than truncating quietly. **The transcript window does not bound it**: a query loads back through its OLDEST match, so the counter, the highlights and the ∧/∨ cycle are always about the whole branch. That reach is a debounced scan (`EARLIER_SCAN_MS`) of the STORED rows above the window, which carries the same asymmetry the branch list lives with (no DOM up there, so a hit that exists only once a display regex rule has run is not seen from it), and it is debounced because find-as-you-type walks prefixes that match far more of the story than the word being typed. Two consequences the bar handles by hand. Until that scan comes back the counter reads "Searching…", never "No matches", which would be a verdict on turns the search has not reached yet. And the cursor is kept by NODE IDENTITY across a load rather than by its number: turns already on screen keep their nodes (the each block is keyed, `renderedHtml` patches in place), while ranges prepended above would slide a numbered cursor onto an older hit. **Off-path branches** (the swipes, alternates and abandoned forks that aren't rendered) are searched as a deliberately separate half: `findBranchHits` matches `allMessages` minus the active path against the same regex, over the STORED text: there is no DOM for them, so no Range and no markdown/display-regex resolution; callers expand `{{char}}`/`{{user}}` first (greetings store their macros raw). They surface as a collapsible "N on other branches" list at the free end of the options row (its own cap, `MAX_BRANCH_HITS`, reported as "N+" the same way), each row a one-line snippet around the first match with the turn's branch label or speaker; clicking one calls `messageStore.navigateToBranch` and sets `pendingTargetId`, which the next match pass claims to land the cursor on that turn's first hit in the freshly rendered path (cleared unconditionally, so a jump that found nothing can't fire later). Reaching a branch is a **click, never part of the ∧/∨ cycle**: a navigation key must not rewrite what the reader is looking at. The bar is centred by auto margins between pinned edges, not `left: 50%` + `translateX(-50%)`: the `.fade-in` entry animates `transform` and would override the centring translate for its whole duration. On wide screens the centered column leaves empty margins flanking it; `ChatContainer` catches `onwheel` over `.chat-content` and forwards it into the `MessageList` scroller (exposed via a `bind:scrollEl` bindable) so the reader can scroll the story from anywhere. It self-limits: an open side dock covers its margin and eats the wheel first, and a chat-covering overlay makes `.chat-host` `visibility:hidden` (so pointer-events-inert): the forward only fires over genuinely empty margin beside a live chat; over the column itself the native scroller already handles it. **It also stands down over any box in the column that scrolls itself**, and this one is not optional: `.chat-content` wraps the **composer** too, not just the transcript, so a blanket `preventDefault()` eats the wheel of every scrollable thing down there (the composer textarea once the draft outgrows its 200px cap, the persona popover's list) and scrolls the story under it instead. `consumesWheel` walks from the event target up to `.chat-content` and bails on the first real scroller (`overflow-y: auto|scroll`, or a `<textarea>`, with `scrollHeight > clientHeight`). It costs nothing on the paths that matter: a wheel over the transcript returns on the `scrollEl.contains` fast path before the walk, and one over the margin has the stop element as its own target, so the loop never enters. Non-scrolling composer chrome (the button row, the meta strip) still forwards. **Message numbers** (`appearance.showMessageNumbers`, toggle on Settings → Layout): `MessageList` passes each turn's 1-based position on the visible path (`ordinal`) through `Message` into `MessageAvatar`, which renders a `#N` badge under the portrait, purely positional, so a delete renumbers everything below; not stored anywhere, and shown in the metadata row for Manuscript or whenever portraits are off (the streaming indicator deliberately carries no number). Its siblings `showTimestamps`/`showModelName`/`showTokenCount` (same settings card) gate the meta row by passing null props from `Message` and `StreamingIndicator`: `MessageMeta` drops the date, and its generation info icon collapses once model and tokens are both null; the reasoning block's `~N tokens` readout in `MessageReasoning` rides its OWN knob, `showReasoningTokenCount`, deliberately independent of the message-level `showTokenCount`. **One pill in that row is a door rather than a readout**: a turn carrying a lorebook trace (`message.lorebook`, architecture/lorebook.md) gets a book pill counting the entries that reached its prompt, and clicking it opens the whole scan. It appears only where a scan actually ran, which `Message` decides and hands down: a turn that consulted no book at all has nothing to report, and a pill reading zero on every reply would be noise for everyone not using lorebooks. It hangs on the REPLY and never on the user turn above it, because a swipe is its own generation with its own rolls, so a pill on the request could only ever describe one of the attempts. **Each generation also names its own kind to the scan** (`lorebookTrigger`: a send is `normal`, either regenerate is `swipe`, Continue is `continue`), since an entry may be limited to some of them and only the caller knows which one is running; a new generation that leaves it out silently reads as a plain send. The token gates sit BEFORE the lazy deriveds on purpose, so the per-message, per-stream-tick, and reasoning-text `countTokens` estimates are all skipped entirely while hidden. **Message card appearance** (Settings → Chat, architecture/ui-shell-settings.md): `Message`, `StreamingIndicator`, `MessageAvatar` and `MessageMeta` carry **no** appearance state of their own: every knob arrives as a `--msg-*` / `--prose-*` / `--avatar-*` custom property, and each declaration keeps the shipped value as its `var()` fallback so the transcript paints right before the theme store boots. Three consequences worth knowing before editing that CSS. **One**: `StreamingIndicator` duplicates the whole card recipe (radius, notch, border, shadow, padding, tail) because the live turn must be indistinguishable from the row it becomes: a var added to `.message-bubble` and forgotten on `.stream-bubble` shows up as the bubble visibly changing shape the instant a reply finishes (coupling 10). **Two**: `showAvatars` off removes `MessageAvatar` from the DOM in JS, not by CSS, because the `#N` ordinal and the generation timer live under the portrait, and a visibility toggle that silently kills two OTHER visibility toggles is a lie. `Message`/`StreamingIndicator` derive `metaReadouts` and hand `ordinal`/`durationMs` to `MessageMeta` when portraits are off or Manuscript is selected. Manuscript uses the shared `MessageHeader` for a compact portrait beside metadata above the speaker name; prose remains full width below it. With portraits off its original inline header stays unchanged; the meta row itself disappears entirely (`hasContent`) once nothing is left to show, rather than leaving a bare strip of padding over the prose. **Three**: knobs a chat style can't honour are hidden in Settings rather than left inert, so the CSS only has to suppress what a style genuinely owns: speaker names are always plain small caps across all chat styles, with Manuscript stacking the name below diagnostics when portraits are on. Actions are always visible and compact, and eligible swipe controls stay visible. The removed appearance fields are ignored at normalization, and the renderer has no dependency on their old CSS variables or attributes.

**The card outline lives on the SHELL, not the card** (`.message-bubble-shell::before`), and this is load-bearing: the ring paints ABOVE the card, which is the only reason it survives the Portraits style, whose card must keep `overflow: visible` for its sticky portrait. So `.message-bubble` keeps a **transparent** border of the same width purely to hold the box model, plus `background-clip: padding-box` so its translucent fill stops at that border rather than stacking with the ring into a denser edge. Consequences: the ghost's dashed treatment and every per-style radius override target the ring, not the card, and a style that wants a different silhouette moves the ring's corners alongside the card's.

**Chat styles** are four `data-chat-style` values stamped on `<html>`, and only three of them change the card. **Bubbles** is the base every rule is written against. **Flat** is Bubbles with the user turn un-mirrored and nothing else: `.message-main-user`/`.message-rail-user`/`.message-toolbar-shell-user` stop reversing, the user tail moves to the left edge with its borders, and the tight notch moves from the top-right corner to the top-left so it still sits nearest the tail. Same cards, same colors, same portrait column, both speakers on the left, which is why Settings gates card knobs on `bubbleLike` (`bubbles || flat`) and `StreamingIndicator` needs no Flat block at all (it only ever renders an assistant turn, which was already left-aligned). **Portraits** and **Manuscript** are the ones that restructure: a two-column card with a sticky in-card portrait, and a full-width card with its compact header above the prose, respectively. Both share card shape, opacity and color settings; opacity zero hides the card surface. A rule keyed to `.message-*-user` in the base block is a rule Flat probably has to undo. Check it there before assuming Bubbles is the only mirrored style. **The delete and regenerate menus hang off `.message-toolbar-shell`, never off `.message-actions-slot`**: the shell spans the whole message column, while the slot is a small box that slides along the toolbar as the branch pager comes and goes, so a menu pinned to the slot's edge leaves the screen on a phone. Two rules ride with that. A style that repacks `.message-toolbar-shell-user` (`justify-content`) sets the matching `.message-menu` edge next to it, or the menu opens away from the toolbar and off the screen. And the menu's cap is `max-width: 100%`, the column, not the viewport: the styles that draw a portrait column take its width off the message column, so on a phone the column is narrower than the menu's 18rem and a viewport-sized cap never engages.

**Message timer** (`showGenerationTime`, same card): `generateResponse`/`generateOpeningScene` no longer clock anything: the server times the generation it writes and stamps `messages.generation_ms` inside `commitGeneratedTurn` (architecture/server-core.md). `continueMessage` is the one story path still holding its own clock, around the `llmService.complete` call alone (no db awaits), and it reports **null** rather than a number when `result.reattached` says the request lived through a dropped socket, since the disconnection would otherwise be added to that turn's stored total for good; `MessageAvatar` renders the formatted readout under the portrait, stacked below the `#N` ordinal (alone when numbers are off or while streaming), from a `durationMs` prop: the saved value on `Message`, a 100ms-interval live elapsed in `StreamingIndicator` (ticking against mount time, which coincides with request start; the interval doesn't run while the knob is off). Like the ordinal it moves into the metadata row in Manuscript or when portraits are off. Greetings, imports, dummies and user turns stay NULL. UI behavior here has no test coverage: the user tests manually.

**Story Map retirement.** The map, minimap, inspector, branch comparison, layout helper and map-only settings have been removed. `/map`, `/canon` and the dedicated annotation writers are retired. Existing message trees, canon pointers and branch labels remain readable and survive duplication and pointer repair; legacy labels still appear in search. Navigation through existing alternatives remains available from the transcript. See [`swipes.md`](swipes.md).

## Chats panel

The browser over the chat list ([`ChatsView.svelte`](../src/lib/components/sidebar/ChatsView.svelte), rows in [`ChatListRow.svelte`](../src/lib/components/sidebar/ChatListRow.svelte)). Everything a row shows beyond the `chats` row itself is a **server-side aggregate**. No message text crosses the wire for the list: `getChatListStats` (per chat: `path`, `total`, `lastAt`), `getChatContentGroups` (identical-chat fingerprints), `searchChatMessages` (opt-in message search), `getChatMemoryFootprint` (what a duplicate would carry). All four live in the "CHAT LIST AGGREGATES" block of `server/db.ts` and are reads, so they carry no sync scope.

**Scope is a switch, not a consequence.** A two-way segmented control under the header picks between the open chat's character and every chat there is, and it writes into `scopedCharacterId`: the SINGLE derived the list, the face each row wears and the New chat button all read, so the panel can never list one thing while its button means another. It is what makes every chat reachable from inside a story without going home first. The choice lives in `uiStore.chatsScope` beside `libraryTab`, kept across opens because a switch that resets on every visit is one the user re-flips on every visit; it names a KIND of scope and never a character, which is what lets it survive walking from one story into another, and it is a preference rather than a binding, so a panel opened with no character on screen lists everything whatever it says. Four rules hold it together. The switch is gated on the library entry **resolving**, not on the chat's character id: a chat orphaned by a character deletion keeps a dangling id, and scoping to that narrows the list to a character with no name, no face and nothing on screen saying why. Those chats browse globally. With no character there is exactly one possible scope, so the switch is hidden outright rather than shown with a permanently dead half, which is a label dressed as a choice. The header title is always "Chats", because the character's name lives in the switch and a title that shape-shifted into it would say the same thing twice, in only one of the two scopes. And a flip empties the held preview and resets the selection like any other filter change: the effect reads `scopedCharacterId` rather than the switch, so the character vanishing from the library under an open panel is covered by the same line. One consequence downstream: the duplicates filter's toggle stays rendered while its own filter is on even once the scope holds no twins, or a flip takes away the only control that can turn it back off.


**Row anatomy**: face, title (+ the twin chip), a relative time under it, a message count at the right edge, and an always-visible row menu. The time is `lastAt`, the active leaf's own timestamp, NOT `MAX(created_at)` over the chat, which would let a swipe written on an abandoned branch date the branch you read. There is no last-message preview line: the only text a row ever carries is the snippet `searchChatMessages` cuts around a hit, shown beside the time so a search result can say why it matched. The favorite **action** lives only in the row menu; the row itself shows a star as state (`.chat-row-star`, drawn with the `heart` glyph).

**Message counts follow the transcript.** The Home cards and Chats rows display `path`: root→`active_leaf_id`, walked in one recursive CTE. The Home and Chats lists pair the number with a chat glyph. Swipes, alternate greetings and abandoned forks do not increase this visible count; there is no separate branch counter. The aggregate still returns `total` (every row in the tree) for deletion confirmations, since deleting a chat removes those alternate turns too.

**Favorites** are `chats.is_favorite` (same shape as `character_library.is_favorite`). `updateChatFavorite` / `chatStore.toggleChatFavorite` deliberately never touch `updated_at`: starring is bookkeeping, and bumping activity would reshuffle the list under the user's cursor. Favorites float into their own section above the day buckets whatever the sort, except when the Favorites filter is already on.

**Duplicate** is one server transaction (`serverDb.duplicateChat`): the chat row and whole message forest receive fresh IDs, with parents inserted before children and all root/active/canon pointers remapped. Settings, character/version binding, feature state, chat-scoped steering and message bookmarks carry over; the chat favorite and composer draft do not. Attachment paths remain shared and reference-counted. Memory is optional: `copyChatMemory` remaps manual scene sources and hierarchy references; stale sources retain their text as reviewable scenes. Compatible historical episodes retain insertion order and are remapped only when all message references survive. Stale or malformed historical rows cannot prevent copying the story. Threads are copied independently using complete-source inheritance. The client registers the copy without opening it. Branching uses the same transaction with only the selected ancestry; see the branch contract below and architecture/memory.md for historical compatibility.

**Identical chats** are found in two stages (`getChatContentGroups`): an aggregate signature in SQL (row count + total content length) narrows the field without reading a byte of content, and only chats that collide on it get hashed. The hash is structural (a node's digest folds in its children's digests, ordered by `(sibling_index, child digest)`), so it is independent of row ids and insertion order, which a copy never reproduces; timestamps are deliberately excluded, so "same story, same text" is the whole test. Attachments are part of the digest (same words over different pictures is a different chat); `thinking` is not (reasoning is the model's scratch paper). Two never-played chats of one character genuinely ARE identical (same seeded greeting, same tree), so they get chipped too; that is the definition working, not a false positive. Chats in a group wear a count chip; hovering it lights every twin, and a filter chip narrows the list to them.

**Search** is two-state by design. Titles always match locally through `buildSearchRegex` (the same case-folding matcher find-in-chat uses). The toggle in the field adds message text, debounced 250ms into `searchChatMessages`, which searches **only each chat's active branch**: off-path hits would need a branch jump to reach, and a result you can't see is worse than no result. Its case fold (`SEARCH_FOLD` in `server/db.ts`) is applied identically in SQL (`foldSearchSql`, to narrow) and in JS (`foldSearchText`, to decide), stops at ASCII + the dotted/dotless i family and five more letters because SQLite's `LOWER()` is ASCII-only, and is one-character-for-one so a match offset still points into the untouched content for the snippet window.

The Chats browser uses a single full-width list at every panel size. There is no message-preview pane or keyboard-hint footer, and hovering or navigating rows never fetches a transcript. Open, Rename, Duplicate, Favorite and Delete remain in each row's menu, reached by its three-dot button or ContextMenu / Shift+F10 for the current keyboard selection. The shared browser controls use the Home funnel button for sorting at every width. In the Chats panel, phones place the search on its own line and expose Favorites, Identical chats (when applicable) and Pick several chats directly below it, without a More chat options menu. The funnel stays at the right edge so its menu opens inside the panel; ascending/descending remain available inside that menu on small screens.

**Keyboard and reach.** The search field and the list are one combobox: focus stays in the field, `aria-activedescendant` names the selected row, and ↑/↓/Home/End/Enter drive it from the window handler. Those keys are bound on the **window**, so they are gated by `listKeysActive()`: the list only gets them when nothing else has focus (the check is "is the focused thing an interactive control other than the search field"). Without that gate the handler ate every Enter in the app: pressing Enter on a row-menu action would open a chat instead. Escape is deliberately ungated. It closes layers, one per press: row menu, sort menu, rename, a typed query, then the panel. Rows and their actions are NOT in the tab order (tabbing through 200 chats to reach one is not reach), so the row menu is opened by the standard **ContextMenu / Shift+F10**. No destructive key is bound: focus lives in a text field, where Delete means "delete a character". The modal wrapper in `Workspace.svelte` carries `role="dialog"` **without** `aria-modal` on purpose: nothing outside is made inert, and claiming modality no focus trap backs up only lies to a screen reader.

Generation-status reads use per-chat request tickets. A newer answer, starting/ending a local stream, or successfully sending Stop invalidates older status snapshots for that chat. While this page owns its stream, it does not classify that same reply through `llmStatus`; starting and ending also clear any hidden same-chat foreign record. After a local stream ends, a fresh status check can still discover a genuine remote generation (for example, one that won the server's single-flight gate). This prevents a delayed status answer from resurrecting a stopped reply and requiring another press of Stop. Covered by the generation-status race tests in `transcript-refresh.test.ts`.

## Before touching this

- Read this + architecture/prompt-pipeline.md (generation) + architecture/memory.md (which tree mutations cost summaries and which are free) first; deletes also interact with chat-image ownership.
- Every tree mutation goes through `messageStore`/`chatStore` methods: never call `db.*` tree methods from a component, and check `warnIfBusy()` semantics before adding a new mutation path.
- Deletes are the most delicate area: attachment ownership, canon repair, active-leaf re-homing, root recompute. Trace one existing delete path end-to-end before writing a new one.


## Hand-kept couplings

1. Sibling navigation is **role-agnostic by design**: `groupSiblings` indexes every child by parent, so the chat arrows/counter walk ALL branches at a point (same-role variants and different-role forks alike) and must include the parent's whole child set. A role filter here makes spliced branches invisible in the transcript; don't add one. Delete re-homing PREFERS a same-role sibling before any-role, but that preference lives in `messages.svelte.ts`, not in `groupSiblings`. **A well-formed tree does not grow a mixed set directly**: both routes that would mint one are shut. A splice at a fork is refused outright (coupling 3), and **Generate/Retry are offered only on the LAST turn of the path** (`showRegenerate` in `Message.svelte` is gated on `isLast` for BOTH roles). The second is the less obvious half: "add alternate reply" on a mid-story user turn would fork a second reply under a turn that already has a child, so once a splice has parked a user turn there, the two become swipe variants of each other. To re-roll from further back the user branches that turn instead (the Branch action: a new chat ends at the copied turn, and Generate is offered on it), which keeps the escape hatch without the mixed set. Indirect routes remain (a lone child spliced away leaves a same-role parent/child pair a later regenerate can fork beside, see `canSpliceMessage`), and imports and older chats already carry mixed sets, which is why the walk stays role-agnostic; don't "clean them up" behind the user's back.
2. Every delete is final, chats included: no grace window exists anywhere for rows or files, and the gate is the confirm BEFORE the act (the destructive-act ladder, architecture/ui-shell-settings.md). `deleteMessageAndDescendants` collects attachment files in the same call and `deleteChat` sweeps rows, attachment files and chat-scoped steering notes in one server call (file-side contract in `server/db.ts`), so nothing may assume a grace window for either. A deferred delete must not come back: its timer dies with the page and the row resurrects on the next boot, while every other device keeps showing the chat for the whole window. The no-undo scan in `contracts.test.ts` holds this.
3. `subtreeBlastRadius` drives message/branch counts and hold duration in delete confirmations. `canSpliceMessage` prevents splicing a branch head that still holds replies, and the server enforces the same rule. Manual summaries are resolved against their saved source signatures: changed or removed sources require review, with their saved text retained. The retired automatic-engine impact/re-read calculations and rebuild-warning UI have been removed; no edit or delete starts model work. See `manual-memory.md`.
4. `chatStore.currentChatState.allMessages` is the snapshot every mutation validates against: long operations must re-fetch rather than trust it, through `chatStore.freshMessages`, never `db.getMessagesByChat`. Same freshness (a server round trip that brings the loaded rows current), priced as a `getMessagesDelta` against the state's `messagesRev` instead of the whole transcript, which on a long chat is the difference between kilobytes and megabytes per swipe (architecture/server-core.md). The merge never mutates the array it replaces, so a caller that keeps the returned array as a snapshot (a pre-delete tree) keeps exactly what it read. **The path is a leaf and rows from one server moment.** `loadChatState` takes the chat row from the same delta answer rather than reading it apart, and `freshMessages` adopts rows only while that answer's leaf is the one the state already draws from. A delete of the turn being read retreats the leaf on the server, so rows adopted under the old leaf walk to nothing: the transcript empties and draws as a fresh chat, opening-scene card and all, for every round trip until the next load. A moved leaf is `loadChatState`'s to publish, together with its rows, in one change. Held by [`message-delete.test.ts`](../src/lib/stores/message-delete.test.ts), which drives each delete shape against the real server database and asserts the transcript changes exactly once. **Two reads of that state overlap constantly**, since a mutation awaits its own refresh while the sync replay `endStream` fires runs unawaited beside it, so the answer that comes back last is not the one that read last. Both writers refuse an answer that is not newer than what the store already holds: `freshMessages` adopts only on a strictly greater `messagesRev`, and `loadChatState` sends its result through `publishTranscript`, which asks `overtaken` before it publishes. That guard needs all three of its questions, because the halves move independently: the reader may have left the chat, a newer load may have published first, and `freshMessages` may have adopted newer rows without claiming a ticket. A rev comparison alone cannot carry it, since a swipe moves `active_leaf_id` and no message row at all, so two loads around one come back at the same rev and the older still wins. Publishing the older answer is not a stale frame the next refresh corrects: a deleted turn comes back, an edit reverts, and the branch being read moves. **The loaded transcript therefore has exactly one guarded publisher**, `publishTranscript`, shared by `loadChatState` and canonical prompt-visibility acknowledgements; a second one anywhere reopens the whole class. Held by [`src/lib/contracts.test.ts`](../src/lib/contracts.test.ts) and by [`transcript-refresh.test.ts`](../src/lib/stores/transcript-refresh.test.ts).
5. Self-ref (`{{char}}`/`{{user}}`) expansion happens live, never baked into rows: display in `Message.svelte`, find-in-chat's off-path branch hits (`ChatSearchBar`), and chats-panel message-search snippets (`ChatsView`), three call sites in all, and generation in `prompt-assembly.toInjectedMessage` + `renderTranscript` (macros.ts) must expand the same way, or the on-screen text and the sent prompt drift. A new surface that renders stored content owes the same call; the macro vocabulary itself is architecture/macros.md. Greetings are seeded raw (`chat.svelte.ts`); nothing re-bakes them. Every one of those three is a read-only surface, so none of them can bake an expanded name back into a row.
6. Find-in-chat has two hand-kept ends: the `data-search-text` attribute on the prose container in `Message.svelte` is the ONLY thing `ChatSearchBar` selects on (drop it and the bar silently finds nothing; it must stay on the story text and stay off the meta row, toolbar and token readouts), and the highlight registry names `chat-find` / `chat-find-current` in `ChatSearchBar` pair with the two `::highlight()` rules in `app.css` ("Find in chat"). Those rules cannot move into the component: CSS highlights are document-scoped by definition, and `::highlight()` honours only colour, background-color, text-decoration and text-shadow. No box properties.
7. Legacy branch labels are read-only annotations in chat search. Their stored palette keys resolve through `branch-labels.ts`; the retired map no longer offers an annotation writer.
8. `duplicateChat` and `branchChat` share their message copy and memory/Threads inheritance ID map. A new message column must be copied explicitly, and every copied message reference must be remapped. Manual scenes with missing sources retain review state; compatible historical episodes require complete references. Forks inherit only summaries and Threads whose complete sources fit the copied prefix. `server/chatList.test.ts`, `server/branchChat.test.ts` and `server/messageBookmarks.test.ts` cover independence, stale historical sources, copied bookmarks and rollback.
9. `StreamingIndicator` mirrors `Message`'s card CSS by hand (`.stream-bubble*` ↔ `.message-bubble*`): the same `--msg-*` vars, the same fallbacks, the same per-chat-style overrides. It is a deliberate duplicate, not an oversight (the two render different content trees), but a card property changed in one and not the other makes the bubble jump the moment a stream lands.
10. Timestamps and durations format through [`time-format.svelte.ts`](../src/lib/utils/time-format.svelte.ts) only, never `toLocale*` at a call site: the locale is always the browser's (an `en-US` date beside prose in another language reads as a bug, which is what this module exists to prevent), and `hour12` is left `undefined` unless the user explicitly picked 12 or 24. Relative labels read `relativeClock.now`, ONE module-level 30s tick shared by every meta row: components must not add their own interval, and reading it outside the `format === 'relative'` guard would drag absolute rows into a re-render they don't need.
11. The chats panel's message search folds case in two places that must agree: `foldSearchSql` (narrows in SQLite) and `foldSearchText` (decides in JS), both driven by the one `SEARCH_FOLD` table in `server/db.ts`. Widening the JS side alone makes the decider accept rows the SQL pass already threw away, i.e. results that depend on which query term happened to be longest.
12. **The greeting list is built in two places and they must build it identically**: `chatStore.seedCharacterGreetings` (what a new chat lays down) and `chatGreetingsOf` in [`server/db.ts`](../server/db.ts), which is BOTH what `refreshSeededGreetings` rewrites a chat to. Same order (First Message, then every alternate), same trim, same drop of empties. The remaining pair cannot be collapsed: one is a client store, the other server-side. A divergence is silent in the worst way: a chat seeded under one rule records a claim its own rows do not match, so the card never reaches it again and nothing anywhere says so. A new trait that seeds a chat (`seedsChat` on `PERMANENT_TRAITS`, architecture/library.md) has to land in both.
13. **Every path that lays greeting rows down must record the claim beside them** (`setChatSeededGreetings`), in the same transaction-shaped moment: `chatStore.seedCharacterGreetings`, `refreshSeededGreetings` after its own rewrite, and `duplicateChat`, which copies the source's claim along with the rows it copies. Rows without a claim are inert (the chat simply never follows the card), so forgetting it in a new seeding path is a feature that silently does nothing rather than a crash. The reverse (a claim without matching rows) is harmless by construction: the match fails and the chat is left alone.
14. **The transcript window is a rendering budget, not a scope.** `MessageList` clips what it draws (see the window paragraph above); nothing downstream may inherit that clip. Everything that READS the story keeps reading `activePath`/`allMessages`: prompt assembly, memory, the chats panel and every blast radius. Everything that POINTS at a turn has to load it back in first, and find in chat does so through `loadThrough`. Any other jump that resolves `document.getElementById('msg-…')` on its own finds nothing for any turn behind the window, and on screen that reads as the turn having been deleted, which is why [`contracts.test.ts`](../src/lib/contracts.test.ts) scans for every shape of that lookup and exempts only the two transcript components that own the window.
15. **The transcript scroller glides by CSS, so a scroll that has to LAND says `behavior: 'instant'`.** `.message-list` is the app's only box carrying `scroll-behavior: smooth`, and that CSS is load-bearing twice: it is the transcript's own feel, and it is the animator `ChatContainer`'s margin wheel rides by writing `scrollTop` and letting it travel. What that costs is a spelling trap. `'auto'` does not override that CSS, it DEFERS to it, and so does a plain `scrollTop` write, so a scroll meant to land travels instead: the reading-position correction after a load then animates and the reader watches the whole stretch that just arrived fly past, worst in the button load mode, where they are parked at the top edge with no gesture of their own to cut the glide short. The deliberate travels (`jumpToLatest`, find in chat's ∧/∨ cycling, `flashTarget`) say `'smooth'` and mean it. Nothing in the type system tells the two apart, since all three spellings are a valid `ScrollBehavior`, so [`contracts.test.ts`](../src/lib/contracts.test.ts) pins that the CSS is still there and still alone, and that neither transcript component asks for `'auto'`.

**Manual prompt exclusion.** The transcript eye button keeps a turn visible but removes it from prompt history, macros, lorebook scanning and memory extraction. It is reversible and synchronized; see [message-visibility.md](message-visibility.md).


Streaming display has its own snapshot (`ChatStore.visibleStreamPreview`). Incoming content and reasoning still append immediately to the raw, chat-owned stream. A shared `CoalescedTask` publishes the latest pair to the UI at most every 50ms, keeping regex, Markdown, DOM patching and stream-driven scroll work on the same cadence. Starting a generation invalidates old scheduled work; ending flushes the last snapshot and then clears both raw/display records after the existing persistence/refresh path. Network delivery, server commits, continuation joins and abort behavior are unchanged. The snapshot is visible only for its owning chat.

Live response/reasoning token estimates use `liveTokenCount` and `LiveTokenCounter`: one trailing update per 200ms, immediate counting for settled text, no tokenization while the corresponding setting is off, and pending estimates cancelled on disable/unmount or a new stream identity. This applies to new replies, reasoning and swipe/replacement readouts. The existing Markdown sanitizer and in-place `renderedHtml` patcher remain in use; batching changes update frequency, not output transformations or DOM identity.

The conversation browsers progressively render chat rows, independently of General → Long chats (which pages messages inside a transcript). ChatsView starts with 50 filtered results and appends 50 within 200px of the scroller end, with a manual Load more chats footer outside the listbox. Group labels and rows use the rendered prefix; filtering, totals, bulk selection, keyboard indexes use the complete filtered set. Keyboard navigation reveals its destination before scrolling to it, including Home/End and wrapping. Option positions and set sizes describe the full result set. Query, message-search mode, scope, sort and filter changes reset the prefix and scroll. Welcome keeps three recent chats while collapsed; its expanded list can load more in batches, and search/filter/selection browsing starts with 50. Its All control likewise names and selects every filtered result, even if only a prefix is mounted. No chat or message data is removed by these presentation limits.

**Branch into a new chat.** `serverDb.branchChat` shares the transactional copy implementation with `duplicateChat`, but selects only the chosen message and its ancestors, including an alternate root when selected. It excludes later turns and sibling alternatives, remaps every copied message id, and sets the new root/active/canon pointers to that linear history. The original chat, pointers and rows remain unchanged. Settings, character/version binding, feature state and chat-scoped steering carry over. Attachments retain the existing reference-counted paths; favorites and composer drafts are not copied. Only memory scenes whose complete message sources fit the prefix are inherited, with hierarchy references remapped; partial/future memory is omitted, and an edited endpoint naturally marks affected inherited memory for review. Threads inheritance uses the same complete-source filter and omits reactions covering an endpoint rewritten in the Branch editor. The client names copies `(branch)`, `(branch 2)`, etc., registers them in the chat list and opens the new chat without a model call. The existing Branch editor and `/branch` still commit through `editMessage(create_branch)`; cancelling creates nothing. Existing internal alternatives remain stored and navigable under their existing rules. `server/branchChat.test.ts` covers boundaries, independence, memory/Threads filtering and rollback.

**Swipe preparation latency.** Regenerate/Swipe obtains a fresh chat/message snapshot and chapter coverage in parallel. It passes that action-scoped snapshot to prompt assembly, avoiding a second history read and a repeated memory read while assembling the same request. Independent library, persona, lorebook, steering, control-value and pinned-version reads run concurrently. After prompt review, the action still re-reads the chat/messages and, for a swipe, chapter coverage in parallel; a changed leaf/chat, hidden/deleted reply or newly covering chapter prevents sending. Nothing is cached across actions or across the review boundary. Opening-scene swipes retain their freshness guards and also parallelize the history/coverage check. `swipe-preparation.test.ts` covers cancellation and changes during review.

**Prompt visibility latency.** `setMessageExcludedFromPrompt` accepts the client's baseline revision and returns the committed message delta with its chat row inside the same transaction. The client adopts that canonical delta without a follow-up transcript/chat request. The mutation claims a load ticket before sending, so older loads cannot restore a previous leaf at the same revision; an intervening newer load/navigation forces a fresh read instead of publishing over it. A failed write changes no local rows. Memory coverage is reconciled against the acknowledged path. Display preprocessing and Markdown rendering are separate derived stages: unchanged expanded/regex-processed text keeps its sanitized HTML even when message objects or visibility flags refresh. Actual text, persona or display-rule changes still update Markdown. These rules are covered by the real-database message revision tests and transcript overlap tests.

Settings → Chat → Interactions offers **Double-click to edit messages** (`generalSettings.doubleClickToEdit`, default off). It rides the synced general-settings spine and opens the same in-place editor as the Edit button. Only rendered story text handles the gesture; links, summary headers, images and embedded controls keep their normal behavior. The shortcut is inert while generation is busy. Touch uses `editOnDoublePress` and the tested `DoubleTapGesture`: two short presses (at most 250 ms each), within 350 ms of each other and 24 CSS px apart. More than 8 px of movement, any captured scroll, pointer cancellation, a second finger, blur, disabling or unmounting clears the sequence. Listeners are passive and global tracking exists only during a pending gesture; native scrolling and text selection are not blocked. Compatibility mouse double-clicks from touch cannot bypass these checks.


## Message bookmarks

A star on `MessageActions` toggles `Message.isBookmarked`. The composer opens `ChatBookmarksDialog`, scoped to the current chat and including saved messages on other swipes. Entries show the story message number, speaker and a plain-text preview; the filled star removes a bookmark without deleting the turn. `chatBookmarks` memoizes ancestor depths and orders entries by message number, then creation time, so alternate swipes stay distinct without rescanning each ancestor chain.

Selecting an on-path entry leaves the active leaf unchanged. An off-path entry deliberately navigates through `messageStore.navigateToBranch` (and respects its generation guard). The dialog closes Find in chat, releases focus, then uses the shared message cursor to load the transcript window through its target and focus the message. No component outside `MessageList` resolves transcript DOM rows. Chat switches close the dialog.

Migration 51 adds `messages.is_bookmarked`, default false. `setMessageBookmarked` updates only that flag and the message revision, returns the committed delta, and broadcasts the existing `messages` sync scope. Metadata writes share the guarded delta publisher with prompt exclusion; bookmarks can be changed during generation. They do not touch chat activity, edit stamps, prompt inclusion, or memory hashes. Message edits keep the flag, copies/branches preserve it on their copied rows, and deleting the message removes its bookmark. SQLite backups include the flag automatically.

## Attachment lifecycle maintenance

Chat attachments are reference-counted across every persisted owner, including inline message
links, library entries/versions and draft presets (`server/image-references.ts`). Row deletion
precedes file release. Malformed ownership data prevents cleanup; an unlink failure after a
committed deletion is logged rather than changing its acknowledged outcome. Boot cleanup
only scans old files under `images/chat/`, including unpaired thumbnails, and retains recent
uploads. Other asset catalogs and backups are not swept.

The composer scopes pending uploads to one chat/lifetime. A late upload cannot populate a
different chat after navigation, and a delayed send commit clears only its original draft.
Pending images are not persisted in text drafts. Navigation does not eagerly delete already
staged uploads because a held send may still reference them; abandoned files are eventually
eligible for the boot sweep.
